# 分类质量验收标准与评测方法（v1）

> 状态：已确认（2026-10-21）
> 来源票：[决策：分类质量的验收标准与评测方法](https://github.com/kostya-sec/AetherHUD/issues/14)
> 依赖决议：#8（纠偏记录载体）、#9（L3 标签治理）、#10（corrections schema）、#11（失败/重试）、#3（抓取降级）、#18（分类建议与分类树演进）
> 本文件是分类器（`src-tauri/src/classifier/`）与评测工具（`src-tauri/src/bin/aether-eval.rs`）的施工依据；实现须以本文件的口径为准。

## 1. 范围与非目标

**范围**：分类质量的口径（指标定义）、目标值与发布门线、评测集规范（规模/分层/标注/存放/版本）、评测执行流程（CLI/触发/判定）、纠偏数据回流闭环、失败与弃权的计分、taxonomy 演进时的版本处理。

**非目标**：

- 分类 prompt 的具体写法（候选池注入、few-shot 编排、上下文截断、弃权指令）——另行设计；
- L1/L2 分类体系的演进与「AI 推荐新类别」的审核机制——另票（本票只约定评测集的版本规则）；
- 分类 provider 的接入与凭证管理（#15）；
- 分类延迟指标——沿用既定基线（P95 < 2s、异步不阻塞入库），本票不另设门槛；
- 评测 UI——v1 只提供本地 CLI，不要求 HUD/设置页入口。

## 2. 分类对象与评测口径

### 2.1 分类体系

- 真源为 `taxonomy.json`（v1.1.0，含 `l1_inbox` / `l2_manual_review`）。**v1 沿用现有分类体系**，本票只评测、不改树。
- L1：4 个正常节点（01 内容与表达 / 02 效率与工作流 / 03 技术与工程 / 04 商业与认知）+「00 未分类」。
- L2：12 个正常节点 +「待人工归档」。L1/L2 是**固定树**，分类器只能从既有节点中选一个，**不得发明新 L1/L2 节点**。
- L3：
  - **形态标签**：固定 5 个（工具 / 教程 / 提示词 / 工作流 / 素材），分类器只能挂、不能新增；
  - **特征标签**：开放集合，AI 可推荐新标签、人工可增删；新增走 #9 的候选池复用 + 归一化 + 别名表；
  - 媒体类型（link/video/article）是条目固有属性，**不评**。
- 模型输出一个 taxonomy 中不存在的 L1/L2 id = **格式非法**（按分类失败处理，见 §5），不是判断错误。
- **弃权时仍输出 L3**（#18）：L1/L2 落到「00 未分类」，形态 / 特征标签照常给；附带的分类建议（最近既有 L2 / 建议新建 L2）属于线索，**不参与任何指标**。

### 2.2 金标（Gold Label）

主评测集每条包含：

- **L1、L2 必标**（唯一答案）；
- **形态标签 1~2 个必标**（这是唯一自动计算指标的 L3 维度）；
- **特征标签 0~3 个**，只标「必须有」的核心标签（用于抽样人工评审，不进自动指标）；
- 媒体类型、难度（easy / hard）、正文快照（≤1500 字）、taxonomy 版本、评测集版本。

金标必须**明确、可判定**。内容本身跨类、无法唯一归类的，不进主评测集，移入**边界集**（§3.5）。

### 2.3 指标定义

| 指标 | 定义 | 分母 |
|---|---|---|
| L1 准确率 | 输出 L1 == 金标 L1 的条目数 / 评测条目数 | 成功分类的条目数 |
| L2 准确率 | 输出 L2 == 金标 L2 的条目数 / 评测条目数 | 成功分类的条目数 |
| L2|L1 条件准确率 | L1 正确的条目中，L2 也正确的比例（仅诊断，不进门线） | L1 正确的条目数 |
| 形态标签 micro-F1 | 对每条计算形态标签集合的 TP / FP / FN，全局汇总后 F1 = 2TP / (2TP + FP + FN) | — |
| 弃权率 | 输出「00 未分类」的条目数 / 评测条目数 | 成功分类的条目数 |
| 分类可用性 | 重试后仍失败（网络终态 / 4xx / 401 / 超时 / 格式非法）的条目数 / 评测条目数 | 全部评测条目数 |
| 特征标签离谱率 | 每版随机抽 20 条人工判定「是否挂了明显错误/离谱标签」的比例，只作观察 | 抽样条目数 |

补充口径：

- **弃权（输出 00 未分类）计入 L1/L2 错误**，同时单列弃权率；
- **分类失败（可用性）不计入准确率分母**，单列报告，避免失败拉低/抬高质量数字；
- **形态标签多标算 FP、少标算 FN**（金标 1~2 个，模型输出也应 1~2 个）；
- 按**金标 L1 分组**报告准确率与弃权率，用于观察偏差，不单独设门槛；
- 按难度（easy/hard）分组报告，观察难例表现，不单独设门槛；
- **不使用模型自报置信度**：结构化输出下 token 概率通常不可得或不可靠，且跨供应商不可比；弃权由 prompt 明示允许，不以置信度阈值触发。
- **分类建议不计分**（#18）：弃权时附带的建议字段只供人工审核，不进准确率 / F1 / 弃权率。

### 2.4 目标值与发布门线

| 指标 | 目标值（努力方向） | 发布门线（不达标不发布） |
|---|---|---|
| L1 准确率 | ≥ 95% | ≥ 90% |
| L2 准确率 | ≥ 90% | ≥ 85% |
| 形态标签 F1 | ≥ 0.80 | ≥ 0.75 |
| 弃权率 | ≤ 5% | ≤ 8% |
| 分类可用性 | ≥ 99% | ≥ 99% |
| 特征标签离谱率 | 观察项 | 不设 |

规则：

- 门线是**硬约束**；目标值只作优化方向，不阻塞发布。
- 首版尚未建立基线时，只看门线；建立基线后，发布还需满足**同一评测集版本、同一 taxonomy 版本下，相对上次基线任一主指标下降不超过 2 个百分点**。
- 2 个百分点的容忍来自小样本抖动（200 条时约 ±3~4pt）；更小的差异不作为回滚依据。
- 换模型或供应商 = **新基线**；绝对门线仍适用，但不与旧模型的成绩做回归比较。

### 2.5 回归拦截

改动 prompt / 模型 / 供应商 / taxonomy 后跑可见集：

1. 任一主指标低于门线 → **不发布**；
2. 相对同条件上次基线下降 > 2pt → **回滚**该次改动；
3. 满足门线且下降 ≤ 2pt → 通过；
4. 报告必须同时给出绝对值和与基线的差值，并附错例供人工判断；数字接近门线时以错例为准。

## 3. 评测集

### 3.1 规模与分层

- **总量 200 条**（首批一次建齐，可分批标注，但门线验收前必须齐）。
- 12 个正常 L2 **每个 ≥ 10 条**（约 120 条）；4 个正常 L1 **每个 ≥ 40 条**（约 160 条）；余量按真实收藏分布补足至 200。
- 媒体形态覆盖：网页 ≥ 60%，视频 ≥ 20%，纯文本 ≥ 10%，其余不限。
- 难例（仅标题、<100 字短内容、跨类模糊、含多语言或噪声）**≥ 20%**，每条标注难度。
- 小样本说明：200 条只能可靠分辨约 8~10 个百分点的差距；1~2 个点的抖动视为噪声，不据此宣布「变好/变坏」。

### 3.2 拆分

- **可见集 150 条**：日常调 prompt 可反复跑、可看错例。
- **盲测集 50 条**：冻结，只在候选版本定稿时跑一次；不得用于调 prompt。
- 按 L1 分层拆分（每类约 75% / 25%），避免盲测集偏科。
- 盲测集与可见集的指标差距 **> 10pt 或连续两个版本同向扩大**时，视为过拟合信号，人工复查；不自动拦截（50 条盲测集本身噪声较大）。
- 盲测集可每季度或评测集版本升级时轮换，轮换必须记录（旧样本回可见集或退役）。

### 3.3 来源与标注

- **首批从用户真实收藏里挑**（冷启动，最有代表性）；后续从纠偏样本审核补充（§6）。
- 单人标注，不做双人一致性（Kappa）；有争议的条目 → 边界集。
- 标注方式：直接编辑 JSONL 或简单本地脚本，不要求 UI。
- 特征标签只标「用户搜索时会用、必须有」的核心标签；宁少不多，避免把个人偏好当金标。

### 3.4 存放与隐私

- 评测集含真实内容，**只存本地**：`app_data_dir/eval/sets/<eval_set_version>.jsonl`。
- **不进 git**；仓库只放空模板与字段说明（`docs/eval/eval-set-template.jsonl`）。
- 报告、候选样本、错例同样只存本地（`app_data_dir/eval/reports/`、`.../candidates/`）；对外分享需脱敏。
- few-shot 示例若含真实内容，也只存本地配置，不入库。

### 3.5 边界集

- 收「内容本身模糊、无法唯一归类、金标有争议」的条目；不参与门线、不计入 200 条。
- 用途：观察模型在这些条目上的弃权/猜测行为；为 taxonomy 演进提供素材。
- 边界集条目在金标明确之前，**不得**移入主评测集。

### 3.6 版本

- 评测集版本形如 `2026-10-v1`，**绑定 taxonomy_version**。
- taxonomy 变更后按 §7 重映射/剔除，生成新版本；已发布版本冻结，不再改。
- **跨 taxonomy 版本或跨评测集版本的指标不可直接比较**；报告必须同时标注 `eval_set_version` 与 `taxonomy_version`。

### 3.7 文件格式

JSONL，每行一个条目：

```json
{
  "entry_id": "01J...",
  "title": "示例标题",
  "url": "https://example.com/...",
  "body_excerpt": "正文前 1500 字快照……",
  "media_type": "link",
  "gold": {
    "l1_id": "l1_tech",
    "l2_id": "l2_coding",
    "format_tags": ["tag_tool"],
    "feature_tags": ["Cursor"]
  },
  "difficulty": "easy",
  "split": "visible",
  "eval_set_version": "2026-10-v1",
  "taxonomy_version": "1.1.0",
  "notes": ""
}
```

## 4. 评测工具契约

### 4.1 CLI

在 `src-tauri` 下运行：

```text
cargo run --release --bin aether-eval -- \
  --set visible|blind|boundary \
  --provider <name> --model <name> \
  --prompt-version <n> \
  [--limit N] [--report <path>]
```

- **复用生产分类路径**：同一 prompt、同一输出校验、同一归一化、同一失败判定；不允许「评测专用分类器」与线上不一致。
- **读生效分类树**（#18）：读 `app_data_dir/taxonomy.effective.json`（缺失时回退底表 `taxonomy.json`），自建 L2 的 id 与名称参与评测。
- 固定条件：provider、model、prompt_version、最低 temperature（0 或 provider 等价设置）；每次运行记录这些参数。
- 串行调用（单 worker），复用生产重试策略；并发会干扰限流与统计。
- 评测读数默认不写生产库（不改 entries），只读本地评测集；需要写库时必须显式开关。

### 4.2 输出

Markdown + JSON 报告，至少包含：

- 参数：评测集版本、taxonomy **底表版本**与**生效版本**、provider / model / prompt_version、运行时间、耗时；
- 总体：L1 / L2 准确率、L2|L1、形态 F1、弃权率、可用性、失败条目数；
- 分 L1：条目数、准确率、弃权率、混淆矩阵（金标 L1 → 输出 L1）；
- 分 L2：每个 L2 的准确率（仅观察）；
- 分难度：easy / hard 的准确率（仅观察）；
- 错例前 20 条：金标 vs 输出、标题、难度、失败原因分类；
- 特征标签抽样 20 条：人工评审结论（回填或单独文件）；
- 未覆盖节点：本次没有任何金标样本的自建 L2 列表（#18 §8.3）；
- 与同条件基线的对比：每个指标的差值；
- 版本校验：底表版本与评测集不一致 → 标注「不可比」；仅生效版本不同 → 标注「生效分类树已变更，本结果为新基线」；评测集引用的自建节点被官方合并时，按 `merged_into` 重映射并提示。

### 4.3 触发时机

- **必跑**：prompt 改动、模型或供应商切换、taxonomy 版本变更、发版前。
- **可选**：纠偏样本积累到批次时（§6）。
- 盲测集只在候选版本定稿时跑；同一候选版本只跑一次，多跑视为污染并记录次数。
- **不接 CI**：无 API key、成本与稳定性不可控；本地手动执行，报告留存。

### 4.4 基线

- 每个「provider + model + prompt_version + eval_set_version + taxonomy_version」组合的第一次运行结果记为基线，存本地报告目录。
- 后续回归比较只与**同组合基线**比；换版本 = 新基线。
- 基线报告不可覆盖；评测报告按时间戳存放。

## 5. 失败、弃权与降级

| 情况 | 判定 | 计分 |
|---|---|---|
| 输出「00 未分类」（可附分类建议） | 弃权（安全行为） | 计入 L1/L2 错误，统计弃权率；建议字段不计分 |
| 输出非法 L1/L2 id、非法标签、空输出、非 JSON | 格式非法 | 分类失败，计入可用性，不计入准确率 |
| API 超时 / 5xx / 429 | 按 #11 重试；重试后仍失败 | 不可用，计入可用性，不计入准确率 |
| 4xx / 401 / Key 无效 | 终态失败 | 不可用，计入可用性 |
| 条目 fetch 失败（fetch_failed） | 无分类输入 | 不进入准确率分母，计入可用性并单列；若金标条目已失效，人工标记退役 |

- 弃权 ≠ 失败：弃权是有意的安全行为，但弃权率超门线说明 prompt 太保守或分类体系覆盖不足；先看错例，再决定改 prompt 还是补分类。
- 分类失败率超过 1% 时，评测报告顶部提示「本次可用性异常，准确率仅供参考」。

## 6. 纠偏数据回流闭环

### 6.1 数据链路

1. 用户在卡片/详情里纠偏 → `corrections` 行（#8/#10 已定，不改表）。
2. 评测工具子命令生成候选：

   ```text
   cargo run --release --bin aether-eval -- candidates --out <dir>
   ```

   - `corrections` JOIN `entries`（`entry_id` 非 NULL）；
   - 取 title、body_md 前 1500 字、media_type、模型当时的输出（`before_value`）、用户金标（`after_value`）、taxonomy_version、created_at；
   - 排除系统迁移、标签合并等非错例（按 dimension/trigger 初筛，仍以人工判断为准）；
   - 按 `entry_id` 去重：一次「采纳建议」会写 L1、L2 两行 corrections（#18 §5），不能产生两个候选；
   - `entry_id` 已置 NULL（条目硬删）的纠偏**没有文本，跳过并计数**，不参与评测。
3. **人工审核**：逐条确认「确实是分类错误、金标稳定」→ 通过；否则丢弃（用户改错、标签合并、条目内容变化、规则变化后不再算错）。

### 6.2 分流

- **通过审核的样本**：
  - 大部分进入评测集下一版本（按 L1 分层，约 75% 可见 / 25% 盲测）；
  - 极少量（每个 L2 最多 1~2 条）进入 **few-shot 示例池**，供 prompt 编排使用。
- **few-shot 池与评测集样本级隔离**：按 `entry_id` + 内容哈希查重，同一内容不得两边都出现；示例池不参与指标计算。
- 审核未通过、但内容确实模糊的 → 边界集。

### 6.3 频率与批量

- 触发：累计 ≥20 条待审纠偏，或距上次审核 ≥30 天，先到者为准。
- 审核与 prompt 迭代解耦：可以先审样本、后改 prompt；不要求每条纠偏立即处理。
- **不做自动注入、不做自动微调、不做在线学习**；所有进入 prompt 的样本必须经过人工审核。

### 6.4 prompt 版本管理

- `settings.classifier.prompt_version` 单调递增。
- 每次改动写 changelog（本地文件或 `docs/spec/classification-quality.md` 附录）：改了什么、为什么、评测报告路径、与上次对比。
- 发布前跑可见集；定稿跑盲测集；不达标或回归超 2pt → **回滚到旧 prompt 版本**。
- prompt 文本与 few-shot 示例存本地配置（不入 git）。

## 7. taxonomy 演进与评测集版本

分类树由**只读底表 + 用户覆盖层**组成，升格只新增自建 L2（#18，见 [taxonomy-evolution.md](./taxonomy-evolution.md)）。

### 7.1 纯加法升格（只新增自建 L2）

- 既有金标样本的 L1/L2 引用全部有效 → **评测集文件不动、不生成新 `eval_set_version`**；
- 但模型选择空间变了 → **必须重跑可见集，结果记为新的基线**（`taxonomy_version` 变化 = 新组合，§4.4）；
- 报告记录底表版本与生效版本；跨版本只记录、不做差值比较（§2.4 / §3.6 的「不可比」继续成立）；
- 未覆盖节点（无金标的自建 L2）报告单列、不参与门线；批量补标时每个节点补 ≥5 条。

### 7.2 非加法变更（将来）

移动 / 删除官方节点、自建节点合并等，按下列规则全量重映射：

1. 金标 L1/L2 按节点 id 重映射；L2 换父节点 → 同步更新金标 L1；
2. 形态标签按 id 重映射（改名不影响 id）；特征标签按归一化 + 别名表转换；合并的标签指向目标标签；
3. 无法映射的条目剔除并记录原因；
4. 生成新评测集版本（`eval_set_version` +1），绑定新 `taxonomy_version`；
5. **跨版本指标不可比**，旧报告保留但不得与新报告直接比较差值。

「分类树如何演进」的完整流程见 [taxonomy-evolution.md](./taxonomy-evolution.md)；本文件只管「版本变化后评测集怎么办」。
