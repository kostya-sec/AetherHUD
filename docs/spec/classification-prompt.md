# 分类 prompt 设计（v1）

> 状态：**已确认**（2026-10-21；HITL 拍板：V-C4 定稿 / 弃权点名「不覆盖主题」/ 8 条 few-shot / 复核跨类金标）
> 来源票：[原型：分类 prompt 设计（taxonomy 注入 + few-shot 编排 + 弃权指令）](https://github.com/kostya-sec/AetherHUD/issues/19)
> 依赖决议：#9（标签候选池 / 归一化 / 别名）、#10（`body_md` 1500 字符上限、id 体系）、#11（失败语义与重试）、#14（质量口径、评测与版本）、#18（弃权与分类建议）
> 施工对象：分类器 prompt 组装（`src-tauri/src/classifier/prompt/`）与评测工具复用同一组装函数（#21）
> 原型产物：[proto/classifier-prompt](https://github.com/kostya-sec/AetherHUD/tree/proto/classifier-prompt) 分支（一次性对比脚本与结果，不并入 main）

## 1. 结论先行

1. **定稿结构 = V-C4**（见 §3 模板）：生效分类树全量注入 + 4 条判定方法 + 标签规则（收紧措辞）+ 特征标签候选池 + 弃权/建议指令 + 输出自检 + 8 条 few-shot + 本地校验与 1 次修复重试。
2. **模型不会自觉遵守计数约束**：朴素 prompt（全量树 + JSON 契约）在 10 条样本上只有 **1 条首轮合规**（其余 9 条 `feature_tags` 给了 4~7 个，超过 3 个上限）。**校验 + 修复重试是硬要求，不是可选优化**。
3. **弃权指令要写「两种允许弃权的情形」并点名「不覆盖的主题」**：实测在可分类样本上 0 弃权（正确），在人工标为「无法唯一归类」的边界集上，弃权从 0/5（抽象措辞）提升到 2/5（点名不覆盖主题）。
4. **成本可接受**：qwen-flash、单条平均 **3.6k 输入 tokens / 36 输出 tokens / ~640ms**（重试时约 1.3s），P95 < 2s 基线有充足余量。
5. **不要用 `response_format: json_schema` 做强约束**：实测 qwen-flash 该模式下输出退化（字段乱序、大量空白、撞 `max_tokens`），改用 `json_object` + 本地逐字段校验。
6. **样本量决定结论强度**：10 条样本只能看「合规率 / 弃权 / 成本」，**准确率差异测不出来**（各版本有效输出都是 9/10）；准确率与门线判定交给 #21 用 200 条金标集跑。

## 3. 最终 prompt 模板（V-C4）

### 3.1 消息结构

一次分类请求固定 4 段：

| 顺序 | 角色 | 内容 | 是否可变 |
|---|---|---|---|
| 1 | `system` | 角色 + 分类树 + 判定方法 + 标签规则 + 候选池 + 弃权/建议 + 输出契约 + 自检 | 只在 taxonomy / 候选池 / 模板变更时变 |
| 2 | `user`→`assistant` | 固定引导语 + 8 条 few-shot 问答对 | 只在 few-shot 变更时变 |
| 3 | `user` | 【待分类条目】字段块 | 每条都变 |

**稳定前缀 + 变化后缀**是有意设计：system 与 few-shot 构成可被 provider 前缀缓存复用的稳定前缀（百炼兼容模式支持上下文缓存），变化内容只放最后一条消息。**不要**把条目字段拼进 system，也不要打乱 few-shot 顺序，否则缓存失效、评测无法复现。

### 3.2 system prompt 模板

```text
你是 AetherHUD 的内容分类器。用户会给你一条自己收藏的内容（标题、链接、媒体类型、正文摘录），你要把它归入固定分类树中的一个 L2，并给出筛选标签。

【分类树】（只能从这些节点中选，禁止发明分类）
{{TAXONOMY_TREE}}

【判定方法】
1. 先判断 L1（内容与表达 / 效率与工作流 / 技术与工程 / 商业与认知），再在该 L1 下选最合适的 L2。
2. 以「用户以后会去哪里找它」为准；跨类时按主要用途归类。
3. 媒体类型不是分类依据：视频、文章只是载体，讲编程的视频归 l2_coding，不因是视频就归「视频与音频」。
4. 标题很短、只有链接或信息不全时，从正文摘录和链接域名判断意图。

【标签】
- format_tags（形态标签）：从固定 5 个 id 中选 1~2 个；多数内容 1 个就够，只有确实同时呈现两种形态（如「工具 + 教程」）才给 2 个。
  tag_tool=工具、tag_tutorial=教程、tag_prompt=提示词、tag_workflow=工作流、tag_asset=素材/资源
- feature_tags（特征标签）：最多 3 个，宁少不多；只取原文里最关键、用户真会用来搜索的专有名词，每个 1~20 字；不要泛词（AI、工具、大模型）。

【特征标签候选池】（优先复用，写法保持一致；确有更准确的新词才新增）
{{TAG_POOL}}

【何时弃权】
只有两种情况允许弃权（输出 l1_inbox + l2_manual_review）：
1. 几乎没有可判断的信息：只有一句噪声、一个域名或裸链接，看不出主题；
2. 主题清楚，但确实不属于分类树里的任何一个正常 L2（共 {{NORMAL_L2_COUNT}} 个）。
其余情况（不确定、跨类、标题短但有正文、在两个 L2 之间犹豫）都要选最可能的一个，不要弃权；弃权率目标 ≤5%。

已知不在覆盖范围的主题例子：通识学习（教材/课程/科普）、生活健康（健身/养生/医疗）、时事新闻（纯资讯）、纯娱乐（段子/追星）。

【弃权时给建议】
弃权时额外输出 suggestion，帮助人快速归置；非弃权时 suggestion 固定为 null。
{"nearest_l2_id":"最接近的正常 L2 id，确实无关联时为 null","new_l2":{"parent_l1_id":"4 个正常 L1 之一","name":"2~10 字的分类名"} 或 null}
- new_l2 只在确有类别缺口时给；名字要短、具体、可复用（如「短视频脚本」「交易与投资」）。
- 建议只是线索、不参与评分；不要为了能填建议而弃权。

【输出】只输出一个 JSON 对象，不要解释、不要 Markdown 代码块。
{"l1_id":"l1_xxx","l2_id":"l2_xxx","format_tags":["tag_xxx"],"feature_tags":["xxx"],"suggestion":null}

【输出前自检】
- l1_id / l2_id 都在分类树中，且 l2_id 属于该 l1_id；
- format_tags 为 1~2 个合法 id；feature_tags 不超过 3 个、每个 1~20 字；
- 弃权时 suggestion 非 null 且字段合法；非弃权时 suggestion 为 null。
```

### 3.3 条目标签块

```text
【待分类条目】
标题：{{TITLE}}
链接：{{URL_HOST_AND_PATH_OR_EMPTY}}
媒体类型：{{网页链接|视频|文章|纯文本}}
视频信息：{{作者 / 平台 / 简介前 300 字}}        ← 仅视频条目且元数据可用时出现，否则整行省略
正文摘录：
{{BODY_EXCERPT_LE_1500}}
```

字段规则见 §4；**不要**给模型看 `entry_id`、`uid`、时间戳、数据库字段名等内部信息。

### 3.4 few-shot 消息

```text
user:      【示例】下面是已核对过的分类示例，注意判定口径与 JSON 形态。
assistant: 好的，请给待分类条目。
user:      【待分类条目】…（示例 1，脱敏后 ≤300 字正文）
assistant: {"l1_id":"…","l2_id":"…","format_tags":["…"],"feature_tags":["…"],"suggestion":null}
…（共 8 条）
user:      【待分类条目】…（真实条目）
```

示例来源、数量、顺序与隔离规则见 §9。**文档里的示例必须是脱敏占位示例**；真实示例（含用户收藏原文）只存本地配置，不入 git（#14 §3.4 / §6.4）。

## 4. 输入装配

| 字段 | 来源 | 规则 |
|---|---|---|
| `TITLE` | 条目标题 | trim；折叠连续空白；≤200 字（超长截断）；为空时用正文首行 |
| `URL` | 原始链接 | 只给「域名 + 路径前 80 字符」，去掉 scheme / query / fragment；纯文本条目省略该行 |
| `MEDIA_TYPE` | 条目固有属性 | 映射为中文（`link`→网页链接、`video`→视频、`article`→文章、`text`→纯文本）；**说明是载体，不是分类依据**（§3.2 判定方法 3） |
| `VIDEO_META` | parser 产出（#2） | 作者 / 平台 / 简介前 300 字；任一项缺失就不写该项，整行都无则省略。B 站字幕、置顶评论不进 prompt（v1 只给简介） |
| `BODY_EXCERPT` | `entries.body_md` | **≤1500 字符**（#10 已定分类上下文长度）；按字符截断，不切半个 UTF-8；连续空行折叠为一个换行；无正文写「（无正文）」 |

**不要**在 prompt 里给模型看的东西：`uid`/ULID、创建时间、同步来源、云端状态位、已有分类结果（重分类时也一样，避免锚定）、纠偏历史。**重分类与首次分类用同一个 prompt**，调用方不传历史分类。

## 5. 分类树注入

- **只注入生效分类树**（底表 `taxonomy.json` ⊕ 覆盖层 `taxonomy.overlay.json`，#18 §3）：官方节点按底表顺序；自建 L2 追加到父 L1 的 children 末尾；**停用节点排除**；`merged_into` 的旧节点不出现。
- 渲染格式（每行一个节点，**id 必须出现**，模型输出 id）：

```text
l1_content 01 内容与表达
  · 文本与写作（l2_writing）｜预设标签：文案、长文、小说、翻译、Prompt框架
  · 图像与设计（l2_image）｜预设标签：Midjourney、StableDiffusion、ComfyUI、风格词、修图、UI设计
l1_inbox 00 未分类（仅用于弃权）
  · 待人工归档（l2_manual_review）
```

- **`l1_inbox` 固定放最后**并标「仅用于弃权」：让 12 个正常 L2 连续呈现、减少「00 未分类」的锚定（原型中 C3 把 inbox 挪到末尾后，首轮合规率 10/10）。
- `l3_preset_tags` 直接渲染在 L2 行内（它同时是标签候选池的一部分，见 §6）。
- **不注入** L3 标签的全部历史、不使用两段式（先 L1 再 L2）调用：分类树只有 12 个 L2，单次调用即可覆盖，两段式会把延迟翻倍、突破 P95 < 2s 的余量。
- 自建节点成本：每个约 +25 tokens；v1 不做裁剪（自建节点 ≥ 20 个时约 +500 tokens，仍在预算内）；超过 50 个再考虑分组注入（留作 v2）。

## 6. 标签规则与候选池

### 6.1 形态标签

- 固定 5 个 id（`tag_tool` / `tag_tutorial` / `tag_prompt` / `tag_workflow` / `tag_asset`），模型只能挂、不能新增（#14 §2.1）。
- 输出 **1~2 个**；措辞强调「多数内容 1 个就够」——实测模型倾向挂 2 个（朴素版本 7/10 挂 2 个），收紧后 9/10 只挂 1 个。
- 多挂算 FP、少挂算 FN（#14 §2.3）；不要为了凑 F1 放宽。

### 6.2 特征标签

- 输出 0~3 个，每个 1~20 字；取原文出现的专有名词/产品名/领域词；禁泛词。
- **候选池** = 当前生效树各 L2 的 `l3_preset_tags`（已在 §5 树里）+ **全局高频特征标签 Top N**。
  - N 建议 **30~40**（约 100~150 tokens）；按 `entry_tags` 使用计数排序（#9 的无状态计数口径），排除形态标签、排除软删墓碑标签。
  - 刷新：随分类 worker 启动 / 每 10 分钟取一次快照；不要求每条实时查库。
  - 提示词只要求「优先复用、写法一致」；**归一化与别名映射在入库后处理**（#9），不放进 prompt。
- 原型中 26 个高频标签的候选池已够用；池子为空（冷启动）时整段省略。

## 7. 弃权与分类建议

- 弃权 = 输出 `l1_inbox` + `l2_manual_review`；此时**照常输出形态/特征标签**（#18 §2.1）。
- **两种允许弃权的情形**：信息量不足（一句噪声、只有域名）；主题明确但不在 12 个正常 L2 覆盖内。其余一律选最可能的一个。
- **点名「不覆盖的主题」**：通识学习 / 生活健康 / 时事新闻 / 纯娱乐。实测这让边界集弃权从 0/5 提到 2/5，同时可分类样本仍 0 弃权。
- `suggestion` 仅弃权时出现，非弃权为 `null`；字段与校验见 [taxonomy-evolution.md](./taxonomy-evolution.md) §2.2：`nearest_l2_id` 必须是生效树里的正常 L2（排除停用与 `l2_manual_review`），`new_l2` 的父 L1 必须是 4 个正常 L1、名字 2~10 字。
- **不给候选列表、不给理由、不给置信度**（#14：不使用模型自报置信度）。
- 防过度弃权：prompt 明说「弃权率目标 ≤5%」「不确定时不要弃权」；实测弃权率监控交给 #21 的评测报告（门线 ≤8%）。

## 8. 输出 schema 与校验

### 8.1 schema（模型输出）

```json
{
  "l1_id": "l1_tech",
  "l2_id": "l2_prompt_agent",
  "format_tags": ["tag_tutorial"],
  "feature_tags": ["Claude Code"],
  "suggestion": null
}
```

| 字段 | 类型 | 约束 |
|---|---|---|
| `l1_id` | string | 分类树中的 L1 id（含 `l1_inbox`） |
| `l2_id` | string | 分类树中的 L2 id，且父子关系必须与 `l1_id` 一致 |
| `format_tags` | string[] | 1~2 个，取值 ⊆ 5 个形态标签 id，去重 |
| `feature_tags` | string[] | 0~3 个，每个 trim 后 1~20 字，去重；不含换行/控制字符 |
| `suggestion` | object \| null | 仅弃权时可非 null；非弃权必须为 null |

**用 id 不用 name**：id 稳定、可校验、不受改名影响；name 只用于日志与 UI。

### 8.2 校验顺序（逐层，遇错即停并聚合错误）

1. JSON 解析（`json_object` 模式下仍可能返回非 JSON 或截断）→ 失败：`parse_error`；
2. 结构：必须是对象，字段类型正确 → `schema_error`；
3. 枚举与层级：`l1_id` 在 L1 集合；`l2_id` 在 L2 集合；`L2_PARENT[l2_id] == l1_id`；`l2_manual_review` 只能配 `l1_inbox` → `enum_error`；
4. 形态标签：1~2 个、id 合法、去重 → `format_tag_error`；
5. 特征标签：≤3 个、长度 1~20、去重（大小写/全半角归一后去重）→ `feature_tag_error`；
6. 建议字段（逐字段独立，丢字段不丢整条，按 #18 §2.2）：`nearest_l2_id` 非法 → 置 null；`new_l2` 非法 → 丢弃该子字段；建议字段**不导致整条分类失败**。

**校验失败 = 分类失败（格式非法）**，计入可用性（#14 §5），不计入准确率；与「弃权」严格区分。

### 8.3 修复重试

- 首次输出失败 → **1 次**修复调用：把原输出作为 `assistant` 消息、把错误清单作为新的 `user` 消息（`上面的输出未通过校验：- …；请只输出修正后的 JSON 对象`），其余消息不变。
- 仍失败 → `classify_failed` + `failure_reason = format_invalid`（可重试，交给 #11 的 job 退避策略）。
- 修复调用计入成本与延迟；**不重复调用超过 1 次**（实测 1 次修复即可把 10/10 拉齐；再多只会放大延迟）。
- 兜底：若上游配置了「无 provider」降级（#15），直接落 `00 未分类` 且**不写 suggestion**（避免伪造线索）。

## 9. few-shot 编排

| 项 | 规则 |
|---|---|
| 数量 | **8 条**：6 条正常分类 + 2 条弃权。不做「每 L2 一条」（12 条 = 多约 1.1k tokens，实测无收益：未给示例的 L2 也被正确归类） |
| 覆盖 | 4 个 L1 各至少 1 条；覆盖易混对：视频教程 vs 视频与音频、教程/工具双形态、写作 vs 社交媒体、提示词 vs 编程；1 条形态标签挂 2 个的例子 |
| 弃权示例 | 2 条：①信息不足（一句噪声）→ 弃权 + `nearest_l2_id`、`new_l2: null`；②类别缺口（通识学习）→ 弃权 + `nearest_l2_id` + `new_l2` |
| 长度 | 每条正文截到 **≤300 字**（控制成本；分类判断不需要满 1500 字） |
| 顺序 | 固定顺序，正常示例在前、弃权示例在后（近因）；**不要**按当前条目动态挑选（评测不可复现、缓存失效） |
| 来源 | 纠偏样本池 → 人工审核通过（#14 §6.2），每个 L2 最多 1~2 条；冷启动期可用人工挑选的历史收藏（本人确认） |
| 隔离 | 与评测集按 `entry_id` + 内容哈希查重，同一内容不得两边都出现（#14 §6.2 / §9） |
| 存储 | 真实示例只存本地配置（`app_data_dir/classifier/fewshot.json`），不入 git |
| 变更 | 任何增删改都升 `prompt_version`，并重跑可见集（#14 §2.5 / §6.4） |

## 10. Token 预算与成本（实测）

qwen-flash、`json_object`、`temperature=0`、`max_tokens=400`、`enable_thinking=false`，2026-10-21：

| 组成 | 实测 tokens | 备注 |
|---|---|---|
| system 段（含分类树 513） | ~1,400 | 树 513；其余规则/候选池/弃权/契约/自检 ~850 |
| few-shot 8 条 | ~2,100 | 单对 ~265 |
| 条目输入 | 115（短标题、正文 61 字）~ 1,024（正文满 1500 字） | |
| **合计输入** | **3,300~3,900** | 原型实测平均 3,577 |
| 输出 | 30~60（平均 36） | `max_tokens=400` 足够 |
| 延迟 | 单次 ~640ms（平均）；重试时 ~1.3s | 串行、单条分类 |

**预算上限**：单次输入 ≤ 4,500 tokens。超出时按优先级收缩：few-shot 8→6（-530）→ 候选池 40→20（-70）→ 视频简介 300→150（-100）。分类树不裁剪（裁树会改变语义）。

**前缀缓存**：system + few-shot 约 3.5k tokens 是稳定前缀，理论上可命中 provider 上下文缓存；原型首轮 `cached_tokens=0`（未预热），生产应以「同 prefix 连续调用」为前提观察命中率，命中后可显著降本降延迟。

## 11. 版本管理

- `settings.classifier.prompt_version`：单调递增整数；prompt 模板、few-shot 集合、候选池规则、校验规则任一变更都 +1。
- **模板与数据分离**：模板骨架入库（本文档 + 代码内常量，不含用户内容）；few-shot 实例与候选池快照存本地配置；每次请求把 `prompt_version`、`template_hash`（模板文本 sha256 前 8 位）、`taxonomy_version`（底表版本 + 生效版本）写进分类日志/评测报告。
- changelog：每次升版本记录「改了什么 / 为什么 / 评测报告路径 / 与上次对比」；位置 `app_data_dir/classifier/changelog.md`（#14 §6.4）。
- 发布流程：改 prompt → 跑可见集 → 过门线且回归 ≤2pt → 跑盲测集 → 定版；不达标回滚到旧 `prompt_version`。
- **换模型/供应商 = 新基线**，不得与旧结果直接比差值（#14 §2.4 / §4.4）。

## 12. 与评测、生产的接口

- 组装函数唯一：生产分类路径与 `aether-eval` 共用 `build_classification_messages(effective_taxonomy, tag_pool, few_shots, entry) -> Vec<Message>`，禁止评测专用 prompt（#14 §4.1）。
- 校验函数唯一：`validate_classification(raw) -> Result<Classification, ValidationError>`，生产与评测共用；评测的「格式非法」判定与线上完全一致。
- 输入类型（描述，不落代码）：`EntryForClassify { title, url, media_type, body_excerpt, video_meta: Option<VideoMeta> }`；`VideoMeta { author, platform, description_excerpt }`。
- 评测固定条件：`provider / model / prompt_version / temperature=0` 写进报告（#14 §4.1）。

## 13. 原型对比（实测记录）

**条件**：10 条真实收藏（取自 `2026-10-v1` 可见集，覆盖 4 个 L1、2 条难例；不含盲测集）；qwen-flash；`temperature=0`；`json_object`；每版本跑 1 次；未做多次重复。

| 版本 | 结构差异 | 首轮合规 | 有效输出 | L1/L2 正确 | 形态 F1 | 重试 | 平均输入 tok | 平均耗时 |
|---|---|---|---|---|---|---|---|---|
| V-A | 全量树 + JSON 契约（朴素） | 1/10 | 1/10 | 1/1 | 1.00 | 0 | 1,175 | 660ms |
| V-B | A + 判定方法 + 候选池 + 6 few-shot | 6/10 | 6/10 | 6/6 | 1.00 | 0 | 2,774 | 619ms |
| V-C | B + 弃权/建议 + 2 弃权示例 + 重试 | 7/10 | 10/10 | 9/10 | 0.87 | 3 | 4,622 | 863ms |
| V-D | C 去掉 suggestion（对照） | 9/10 | 10/10 | 9/10 | 0.87 | 1 | 3,657 | 718ms |
| V-C2 | C + 收紧标签措辞 | 9/10 | 10/10 | 9/10 | 0.95 | 1 | 3,866 | 695ms |
| V-C3 | C2 + `00 未分类` 挪到树末尾 + 弃权措辞 v2 | 10/10 | 10/10 | 9/10 | 0.91 | 0 | 3,531 | 639ms |
| **V-C4** | **C3 + 点名「不覆盖主题」** | **10/10** | **10/10** | **9/10** | **0.95** | **0** | **3,577** | **642ms** |

**边界集弃权观察**（5 条人工标为「无法唯一归类」的条目，不参与门线）：V-C2 弃权 0/5；V-C3 1/5；V-C4 2/5。可分类样本上各版本弃权均为 0/10。

**结论与解读**：

1. **没有校验重试的版本（A/B）不可用**：首轮合规率 1/10、6/10，失败全部来自 `feature_tags` 超过 3 个（A 有 6 条给 5 个、1 条给 7 个）。说明计数类约束必须由校验器兜底。
2. **候选池 + few-shot 有正向作用但不足以解决合规**：B 比 A 好，但仍有 4 条超限；仅靠示例不能替代校验。
3. **收紧措辞显著降低重试**：C2/C3/C4 把「最多 3 个、宁少不多」「多数内容 1 个形态标签」写进标签规则后，重试从 3 次降到 0~1 次；形态标签的 precision 从 0.77（C/D）提升到 0.91（C2/C4）。
4. **`suggestion` 字段本身不拖累分类**：C vs D（有/无建议字段）在有效输出、弃权率、准确率上无差异，token 只多约 1k（因 C 多一条弃权示例与建议规则）；#18 的接口可以放心保留。
5. **准确率测不出差异**：唯一错例 T9 在所有版本里都判成 `l1_tech/l2_ops_infra`（金标 `l1_biz/l2_insight`），属金标或 prompt 都可能在错；等 #21 的 200 条评测再看。
6. **json_schema 强约束不可用**：另测 `response_format: json_schema`（enum + maxItems + strict）在 qwen-flash 上输出退化（字段顺序乱、出现大段空白、`finish_reason=length`），且 DashScope 兼容层不保证强约束 —— 改用 `json_object` + 本地校验。

**局限**：

- 10 条样本、单次运行、temperature=0 仍有轻微非确定性（同一版本两次结果可能差 1 条）；数字只作方向性判断。
- 金标标签本身有个别争议（见 T9），会污染准确率读数。
- 弃权与 suggestion 的质量未真正验证：可分类样本 0 弃权、边界集仅 2 条弃权，样本量不足以判断建议字段的可用性。
- 候选池的实际收益未隔离验证（B 同时加了判定方法、候选池、few-shot）。
