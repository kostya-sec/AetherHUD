# 分类树演进：分类建议、采纳与升格（v1）

> 状态：已确认（2026-10-21）
> 来源票：[决策：分类体系演进——AI 弃权时的类别推荐与人工升格机制](https://github.com/kostya-sec/AetherHUD/issues/18)
> 依赖决议：#8（纠偏记录与卡片操作）、#9（L3 标签治理）、#10（SQLite schema 与 taxonomy 版本迁移）、#14（分类质量与评测集版本）、#17（键盘导航与焦点）
> 本文件是分类器（`src-tauri/src/classifier/`）、分类树加载与合并、未分类审核 UI、设置「分类管理」页与评测工具（`aether-eval`）的施工依据。

## 1. 范围与非目标

**范围**

- 弃权时的输出契约：分类建议（最近既有 L2 / 建议新建 L2）、校验与计分；
- 建议的存储与呈现；
- **采纳**（归入既有 L2，等同纠偏）与**升格**（新增自建 L2）两条链路；
- 分类树落地形态：只读底表 + 用户覆盖层（文件格式、合并、升级、备份）；
- 自建节点的停用 / 恢复 / 删除 / 改名；
- 版本与评测口径（对 #14 §7 的加法式澄清）。

**非目标**

- 分类 prompt 的具体文本与 few-shot 编排（#19）；
- 评测 CLI 与评测集的实现 / 标注（#20 / #21）；
- L3 标签治理（#9）与形态标签（固定 5 个，不可新增）；
- 应用内新增 **L1**（v1 明确不做，见 §3.2）；
- 多用户 / 多机同步。

## 2. 弃权与分类建议

### 2.1 局部弃权

- 分类引擎无法把条目归入既有 L1/L2 时，输出 `l1_inbox` / `l2_manual_review`（「00 未分类 / 待人工归档」），**同时照常输出形态标签与特征标签**。
- 弃权只表示「落位失败」，不表示「内容读不懂」：L3 与 L1/L2 正交，且 #9 已允许 AI 直接创建特征标签。未分类卡片照常显示标签，人工审核时标签也是线索。
- 计分不变（#14 §2.3 / §5）：弃权计入 L1/L2 错误并单列弃权率；形态标签 micro-F1 照常计算；**分类建议本身不计分**。

### 2.2 分类建议（输出契约）

弃权时，分类结果额外携带 `suggestion`：

```json
{
  "l1_id": "l1_inbox",
  "l2_id": "l2_manual_review",
  "format_tags": ["tag_tool"],
  "feature_tags": ["AI剪辑"],
  "suggestion": {
    "nearest_l2_id": "l2_video_audio",
    "new_l2": { "parent_l1_id": "l1_content", "name": "短视频脚本" }
  }
}
```

规则：

1. `suggestion` **仅弃权时出现**；非弃权时为 `null`（不输出）。
2. `nearest_l2_id`：最接近的既有 L2，必须是生效分类树里的正常 L2（12 个官方 L2 + 启用中的自建 L2，排除停用节点）；确实毫无关联时为 `null`。
3. `new_l2`：确实缺类别时才给；`parent_l1_id` 必须是 4 个正常 L1 之一（不得为 `l1_inbox`），`name` 规则见 §6.2。
4. 两者可同时存在，也可都为空；**不给候选列表、不给理由文本、不给置信度**（#14：不使用模型自报置信度）。
5. 建议只是线索，处置权在人（§5 采纳 / §6 升格）。

**校验与失败处理**（逐字段独立，丢字段不丢整条）：

| 字段 | 校验 | 失败处理 |
|---|---|---|
| `nearest_l2_id` | 存在于生效树的正常 L2（官方或启用中的自建，排除停用），且不是 `l2_manual_review` | 置 `null` |
| `new_l2.parent_l1_id` | 属于 4 个正常 L1 | 整个 `new_l2` 字段丢弃 |
| `new_l2.name` | trim 后 2~10 字符、无控制字符 / 换行 / 斜杠（§6.2） | 整个 `new_l2` 字段丢弃 |
| `suggestion` 出现在非弃权结果 | —— | 忽略（视为格式错误，不落库） |

- 校验失败**不**导致分类失败（可用性口径不变，见 #14 §5）。
- 名字与既有节点重名**不在存储时拒绝**——建议属于原始线索，界面按 §5.3 自动转成「归入同名节点」。

### 2.3 与 prompt 的接口（#19）

- prompt 必须同时包含「何时弃权」与「弃权时给建议」两条指令；**不得因为要填建议而放宽弃权条件**，弃权率门线（目标 ≤5% / 门线 ≤8%）不变。
- taxonomy 注入使用**生效分类树**（含自建节点，排除停用节点），否则分类器永远学不会自建节点。
- 建议字段的 token 成本可忽略（每条约 20~40 tokens），一律只输出短名。
- `docs/spec/classification-prompt.md` 需覆盖：弃权判定措辞、建议字段的 few-shot、非法建议的纠正示例。

## 3. 落地形态：只读底表 + 用户覆盖层

### 3.1 为什么不能写 taxonomy.json

`taxonomy.json` 随安装包分发：macOS 在 `.app` 包内（改它破坏签名），Windows 在安装目录（升级会覆盖）。应用内升格必须写到用户可写、且升级不受影响的位置。

### 3.2 三个文件

| 文件 | 位置 | 读写 | 内容 |
|---|---|---|---|
| 底表 | 安装包资源 `taxonomy.json` | 只读 | 官方 L1/L2、形态标签、版本号 |
| 覆盖层 | `app_data_dir/taxonomy.overlay.json` | 读写 | 仅自建 L2 与合并映射 |
| 生效分类树 | `app_data_dir/taxonomy.effective.json` | 只写 | 启动 / 升格后导出的合并结果，供调试、评测工具与校验脚本读取 |

- **生效分类树 = 底表 ⊕ 覆盖层**，运行时载入内存；官方节点保持底表顺序，自建节点按 `created_at` 追加到父 L1 的 children 末尾。
- v1 只允许在 4 个正常 L1 下新增 L2；新增 L1 只能随版本发布（改底表）。

### 3.3 覆盖层格式

```json
{
  "format_version": 1,
  "base_version_seen": "1.1.0",
  "revision": 3,
  "nodes": [
    {
      "id": "l2u_01J9Z6Q2X8V4B7N3M5K1T0R6CP",
      "parent_l1_id": "l1_content",
      "name": "短视频脚本",
      "l3_preset_tags": [],
      "status": "active",
      "created_at": 1761000000000,
      "created_from": {
        "entry_uid": "01J9...",
        "suggestion": { "parent_l1_id": "l1_content", "name": "短视频脚本" }
      },
      "renamed_at": 1761000000000,
      "disabled_at": null
    }
  ],
  "merged_into": [
    { "from": "l2u_...", "to": "l2_official_id", "at": 1761000000000 }
  ]
}
```

- `id` 固定为 `l2u_` + 26 位 ULID；官方 id 不使用 `l2u_` 前缀，因此永不冲突。
- `status`：`active` / `disabled` / `merged`。
- `revision`：覆盖层内容的单调修订号，任何变更（新建 / 改名 / 停用 / 恢复 / 删除 / 合并）+1。
- `base_version_seen`：最近一次与底表对账时的底表版本。
- 写入一律「临时文件 + 原子 rename」，不出现半个 JSON。

### 3.4 生效版本号

- `<底表 version>+u<revision>`，例如 `1.1.0+u3`。底表升级时底表段变化、`revision` 默认不变。
- `meta.taxonomy_version`（#10 §3.8）存**生效版本**。
- 评测集与报告同时记录**底表版本**与**生效版本**（§8）。

### 3.5 启动流程

1. 读底表；
2. 读覆盖层（不存在则创建空覆盖层，`revision = 0`）；
3. 校验：父 L1 存在、id 唯一、同一父 L1 下名字规范化唯一、字段合法；
4. 合并 → 内存生效树；
5. 校验 `meta.taxonomy_version`：
   - 不一致 → 按 #10 §10 备份 DB、失效引用重映射到 `l1_inbox/l2_manual_review`、更新 meta；
   - 覆盖层损坏 / 非法 JSON → 备份为 `taxonomy.overlay.corrupt-<ts>.json`，以底表启动（不做合并），失效引用按 #10 §10 重映射到 `l1_inbox/l2_manual_review`；HUD 内一次性 5 秒提示条告知（复用 #13 的提示条机制，不抢焦点）；
6. 原子写 `taxonomy.effective.json`。

### 3.6 备份

- 覆盖层随 DB 一起备份：`backups/aether-<ts>.db` 旁写 `backups/taxonomy.overlay.<ts>.json`，保留最近 5 份（沿用 #10 §11 / #13 的既有策略）。
- 覆盖层极小（< 10 KB），备份成本可忽略。

## 4. 存储：entries.classify_suggestion

`entries` 新增一列（v1 DDL 直接加；仓库尚无代码，不写迁移）：

```sql
classify_suggestion TEXT  -- JSON 快照；仅弃权条目非空
```

内容 = §2.2 的 `suggestion` + 生成时的生效版本：

```json
{
  "nearest_l2_id": "l2_video_audio",
  "new_l2": { "parent_l1_id": "l1_content", "name": "短视频脚本" },
  "taxonomy_version": "1.1.0+u0"
}
```

- **写入**：分类结果落库时写。
- **清空**：任何 L1/L2 变更（采纳、升格迁移、手动纠偏、重新分类）都置 `NULL`。
- 不建建议表；「同建议还有 N 条」在应用内对未分类条目（`l2_id = 'l2_manual_review'`）做统计，数据量很小。该 JSON 不参与 SQL 过滤 / 排序（贴合 #10 §2 的「JSON 仅限不可查询快照」约定）。

## 5. 呈现与交互

### 5.1 入口

- 球列「00 未分类」L1 球（#17 §5.4，5 个球之一）→ L2 面板「待人工归档」→ 卡片流。
- 不新增 HUD 层页面、不新增全局快捷键；设置页新增的「分类管理」见 §7。球是否带计数徽标沿用 #17 的球列规则。

### 5.2 卡片行

未分类卡片在分类路径下方多一行淡色建议（其它视图不显示）：

| 情况 | 文案 |
|---|---|
| 只有最近既有 | `AI 建议：03 技术与工程 › 编程与低代码` |
| 有建议新建 | `AI 建议：新建「短视频脚本」（01 内容与表达）` |
| 两者都有 | 主行显示建议新建；详情里两者都列 |
| 都没有 | 不显示该行，只保留「未分类」徽标 |

### 5.3 详情弹窗（Space，沿用 #17 §5.7）

新增「AI 建议」区块：

- **最近既有 L2**（如有）→ 按钮「按建议归入」；
- **建议新建**（如有）→ 按钮「新建分类…」；若同一父 L1 下已存在同名节点（例如刚刚升格过），则改显示「归入『X』」按钮（走采纳，不再提供新建）；
- **计数**：「同建议还有 N 条」（同父 L1 + 规范化名字相同、仍处于未分类）；
- **软提示**：N = 1 →「只有这 1 条，确定要新建类别？」；该 L1 下自建 L2 ≥ 7 →「该分区自建分类较多，先看看能否并入现有节点」；
- **两者都没有** →「没有建议，手动改分类」。

键盘：按钮进入 Tab 顺序；不加新快捷键；不做多选批量（#17 v1 明确不做）。

### 5.4 结果反馈

- 采纳：toast「已归入 03 技术与工程 › 编程与低代码」；
- 升格：toast「已新建分类『短视频脚本』并移入 N 条」；
- 列表即时刷新（未分类视图条目减少；新节点出现在 L2 面板末尾）。

## 6. 升格

### 6.1 表单

| 字段 | 默认 | 说明 |
|---|---|---|
| 名字 | 建议的 `new_l2.name` | 可改，规则见 §6.2 |
| 父 L1 | 建议的 `parent_l1_id` | 只在 4 个正常 L1 中选，可改 |
| 一并移入同建议条目 | 勾选 | 显示「共 N 条」，取消则只挪当前条目 |

### 6.2 名字规则

- trim 后 **2~10 个字符**（按 Unicode 字符计）。
- 规范化（去首尾空格、连续空白折一、拉丁大小写折叠、全半角统一）后，与**所有现有 L1/L2 名称**（官方 + 自建 + 停用）唯一。
- 禁控制字符、换行、斜杠 `/`、反斜杠。
- 不鼓励数字前缀（官方风格是「01 内容与表达」），但不强制拦截。

### 6.3 执行步骤（文件原子写 + DB 事务）

1. 校验；
2. 生成 `l2u_<ULID>`；
3. 原子写覆盖层：nodes 追加、`revision + 1`、`base_version_seen` = 当前底表版本；
4. 重算内存生效树；
5. DB 事务：更新 `meta.taxonomy_version`；迁移条目——当前条目 +（勾选时）同建议条目 → `l1_id / l2_id` 指向新节点、`corrected_by = 'human'`、`classify_suggestion = NULL`；
6. 事务失败 → 用事务前快照回写覆盖层并报错，不允许出现「树里有节点、条目没迁」；
7. 导出 `taxonomy.effective.json`；
8. toast，并提示「分类树已变更，请重跑可见集建立新基线」（§8）。

- **不写 corrections**：这是分类树迁移，不是模型错例（与 #10 §10「失效引用重映射不写 corrections」同口径）。

### 6.4 同建议条目匹配

- 条件：`l2_id = 'l2_manual_review'`，且 `classify_suggestion.new_l2.parent_l1_id` 相同、名字规范化后相同；
- 不做模糊匹配；「最近既有」建议不参与批量（那条走采纳）。

## 7. 自建节点的停用、恢复、删除、改名

| 操作 | 规则 |
|---|---|
| 停用 | `status = 'disabled'`：不出现在 L2 面板、不参与分类候选（prompt 注入排除）、不再可选；已归属条目保留、显示名照常解析；可随时恢复 |
| 恢复 | `status = 'active'`，`revision + 1` |
| 删除 | **仅当节点下条目数为 0**（含 active / 封存 / 回收站全部 lifecycle）；从覆盖层移除，`revision + 1` |
| 改名 | 只改 `name`，id 不变，不写 corrections；规范化唯一校验同 §6.2，`revision + 1` |
| 官方节点 | 应用内不可停用 / 删除 / 改名 |

- 管理入口：设置球展开条新增「分类管理」页（与 #9「标签管理」同级），列出自建节点（名称 / 父 L1 / 条目数 / 状态）与上述操作；**新建入口仍只在未分类详情**（§6）。
- 停用节点的分类结果不再产生；已有条目的 `l2_id` 指向停用节点时，条目仍可正常展示与搜索。

## 8. 版本与评测（对 #14 §7 的加法式澄清）

### 8.1 纯加法升格

「纯加法」= 只新增自建 L2（不改 / 不删 / 不移动任何官方节点，不改任何既有 id）。此时：

- 评测集**文件不动**：既有金标样本的 L1/L2 引用全部有效，不需要重映射，也不生成新的 `eval_set_version`；
- 但模型的选择空间变了 → **必须重跑可见集，结果记为新的基线**（`taxonomy_version` 变了，按 #14 §4.4 即新组合）；
- 报告同时记录 `taxonomy_base_version` 与 `taxonomy_effective_version`；**跨版本只记录、不做差值比较**（#14 §2.4 / §3.6 的「不可比」继续成立）。

### 8.2 非加法变更（将来）

若未来支持移动 / 删除官方节点或自建节点合并，仍按 #14 §7 全量重映射、生成新的评测集版本；跨版本不可比。

### 8.3 未覆盖节点

- 自建节点标记「未覆盖」；评测报告单列「未覆盖节点：N 个」，**发版门线仍按原有 12 个正常 L2 / 4 个正常 L1 统计**；
- 下次批量补标（累计 ≥20 条待审纠偏或 ≥30 天，见 #14 §6.3）时，为每个未覆盖节点补 **≥5 条**金标，随下一次评测集版本一起加入（按 L1 分层进可见集）；补上后单列统计，不改变原有门线分母，但评测集版本会因此 +1（样本变更）。

### 8.4 工具衔接

- `aether-eval` 与评测集校验脚本读 `app_data_dir/taxonomy.effective.json`（缺失时回退底表）；报告回显双版本。
- 评测集 JSONL 的 `taxonomy_version` 记**标注时的生效版本**；校验以**底表版本**为准（生效版本不同只标注「生效分类树已变更，本结果为新基线」，不判错）。
- 纠偏候选生成按 `entry_id` 去重：一次采纳会写 L1 / L2 两行 corrections（§5），不能因此产生两个候选。

## 9. 与 #9 的边界

- **特征标签**：AI 直接创建（`origin = 'ai'`）、条目级可见、≥2 次使用自动进筛选栏；人工增删即纠偏。**不经过分类建议 / 升格**。
- **形态标签**：固定 5 个，AI 只能挂不能新增。
- **L3 标签与 L2 节点是不同命名空间**：允许同名（如 L2「短视频脚本」与特征标签「短视频脚本」），不强制关联，也不自动把建议名建成标签。
- **标签管理页不管理 L1/L2**；分类树管理走 §7 的「分类管理」页。
- #9 的「标签爆胀」闸门（使用数 ≥2）不适用于 L2 节点：节点是人建的，不以使用数自动升降。

## 10. 升级撞名与合并

- 触发：底表升级后，官方新增节点与自建节点「同父 L1 + 规范化名字相同」。
- 处理（**官方优先**）：自建节点条目改指官方节点 → 自建节点 `status = 'merged'` → 覆盖层 `merged_into` 记录 `{from, to, at}` → `revision + 1`。`merged` 节点不进入生效分类树（只为映射保留）。
- 评测集若引用被合并的 `l2u_` id：评测工具按 `merged_into` 自动重映射，并在报告提示「N 条金标已按合并映射重映射」。
- 纠偏记录（corrections）保留原快照不动（历史事实）。
